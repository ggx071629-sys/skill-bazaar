# 技术选型与决策记录

帮助用户形成适合当前项目、能解释取舍且可追溯的技术决策。保持推荐明确、状态准确，按用户需要控制讨论深度；不预设语言、框架、数据库或供应商。

## 从已有约束开始

先阅读目标项目适用的指令、产品说明与现有选型记录。区分已确认需求、产品设想和历史讨论，不把尚未确定的业务规则补成正式需求。

优先识别会改变主要路线的约束：

- 产品形态、目标平台，以及是否要求共享页面或只是共享数据与业务规则。
- 核心体验、AI 等能力的实际用途、维护能力和已有代码或团队经验。
- 当前阶段与讨论范围，例如只做开发期选型，还是包含部署和发布。
- 当供应商、可用性或成本进入讨论时，再明确服务地区和预算。

已有信息足够时直接推进。只有缺失信息会影响当前结论时再问，不为凑齐清单反复询问。用户已授权或确认的选择不重复索取确认。

## 推荐与证据

给出当前首选，说明它解决什么问题、承担什么成本，以及哪些新约束足以改变推荐。备选用于解释实际取舍，不把每个方案都说成同样推荐，也不因用户坚持而无依据地改变判断。

需要比较当前版本、兼容性、生态、成本或平台限制时，优先核对官方文档、版本化源码、依赖声明和发布记录。只记录用户刚确认的决定时，不必重做研究。

使用案例时区分：

- 案例展示与可检查源码；品牌采用某个模块与整个产品采用同一技术栈。
- 历史可行性与当前依赖组合的兼容性。
- 框架的总体社区与其特定平台适配层的资源。
- 用户量、Stars、搜索结果数量与真正可复用的排障资料。

不要据少数案例声称“社区公认最优解”、市场份额或问题解决率。不编造复用比例、开发提速、维护倍数或性能排名。明确区分已核实事实、工程判断和待验证事项；网络不可用时保留未知，不补出供应商价格或兼容性结论。

## 按用户需要收敛

先讨论能影响整体架构和维护成本的决策，再处理实际功能需要的配套细节。比较范围由项目决定，不要求每个项目都配置 AI、向量库、微服务或复杂工程工具。

用户希望逐项讨论时，每次聚焦一个对整体有影响的选择；一项确认后及时记录，再进入下一项。用户希望直接给整体方案时，提供有依据的整体建议，不强制逐个投票。

用户只问“是什么”或“能做什么”，先解释，不把问题当作采用确认。用户明确采用一套方案时，只提升被确认部分的状态，附带举例或未来扩展继续保持建议状态。

给不熟悉技术的用户解释时，用“解决的问题＋一个具体例子＋与已有组件的关系”，控制术语数量。准确区分语言、框架、能力、方法和服务；选定框架不代表已经选定模型、存储扩展或具体工作流。

当主要路线已覆盖首期核心流程、重要未知已有明确边界和验证路径时，可以判断选型足够。不以“所有工具库都选完”为完成标准。用户要求简化或排除上线事项时，立即调整当前清单，保留已确认选择，把实施细节后移。

## 维护决策记录

用户要求记录时，遵循指定路径与现有文档格式，更新现有文件或创建必要的选型文档。没有记录授权时，先在对话中给出建议；不因选型讨论自动初始化项目、安装依赖或创建外部资源。

让当前采用方案容易找到。按实际复杂度记录：项目约束、主要架构与选型、组件职责、共享和分端边界、关键取舍，以及开发时仍需明确的事项。来源靠近所支持的结论；深入研究与当前决策分工清楚，避免维护多份相互冲突的现状。

区分以下状态：

| 状态 | 含义 |
| --- | --- |
| 已选 | 用户已明确采用，或既有授权允许确定的选择；注明是否尚未实现或验证 |
| 建议 | 当前推荐，尚未确认为项目决定 |
| 待定 | 仍需要产品信息、比较或验证 |
| 备选 | 明确条件变化时再评估的路线，不与当前已选并列为实际架构 |
| 历史／已调整 | 保留讨论背景，但不继续作为当前要求 |

确认后同步更新概要、正文和待定清单，删除对应的过时“下一项”或“尚未确认”表述。只同步确有关系的入口与引用文档，保留其他工作和无关内容。

描述共享能力时区分：共用代码、共用接口约定、共用设计规范和共用后端数据。单仓库不等于代码全部复用；类型生成不等于页面自动更新；前后端分离与同仓库管理可以同时成立。核心规则在哪一层执行、哪些平台调用需要适配，应明确到职责，不必细列全部实现库。

把“选型确定”“代码已实现”“构建通过”“真机或运行时验证通过”分别记录。模拟服务或类型检查只能支持其实际覆盖的结论。

## 一致性复核与完成

复核围绕本次选择与讨论范围，不升级为全项目审计：

- 概要、正文和相关产品文档是否存在状态或职责冲突。
- 已确认选择是否被遗漏、仍标待定，或与备选混在一起。
- 共享边界、接口与数据库模型、AI 框架与模型实现是否被混为一谈。
- 数据归属、个人文件、检索资料范围等开发边界是否缺失；只补齐待设计事项，不代替用户新增功能或敲定业务规则。
- 模型、索引或持久化等能力是否被误写成已经实现的正确性保证。
- 是否继续要求用户确认已排除的部署事项或不必要的工具细节。

在已授权的文档维护范围内直接修正明确的不一致；影响技术路线或业务规则的未知保持待定。检查本地引用与文档格式，并核对已确认方案未被误改。除非进行了实际构建或运行验证，不把文档检查说成技术方案已经验证。

结束时简要给出当前结论、记录位置、实质变更和剩余关键未知。选型足够时明确收敛，下一步回到首期功能、数据模型与接口设计；不为延长流程继续推荐新依赖。
