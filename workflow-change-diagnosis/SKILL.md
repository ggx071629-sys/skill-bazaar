# 工作流改动归因

解释一次具体结果为什么出现，以及它与本轮改动有什么已证实或尚未证实的关系。规则缺陷、实际执行和验收误判可以同时存在，不强行二选一。

## 1. 明确异常与调查范围

读取目标工程约定、用户原始要求、具体结果与反馈，先把「变差了」落到可检查的现象：哪件产物、哪个版本、什么位置、与什么目标不符。区分用户明确的要求、局部偏好和助手自己的判断；不直接把任何一方对原因的解释当成结论。

已有定位足够时直接调查。只有对象、比较版本或预期存在会改变结论的歧义时才补问，其他独立取证继续进行。通常先查一个有代表性的失败实例，再按需要扩展，避免无差别重读全工程。

仅请求归因时保持目标工程、规则、产物和完成状态只读，不先改规则或重制成品。用户同时授权修复时，先保留能支持改前判断的材料，再处理已定位问题；不能用修后现场冒充改前现场。

## 2. 找到本轮真正的前后版本

从提交、任务快照、备份、原始输入、运行记录或交付回执定位版本，核对它们与本次改动的时间和对象是否对应。需要时记录路径、修订号、文件摘要和来源；文件名、修改时间或「已优化」的表述不能单独证明身份。

- Git HEAD 可能早于多轮未提交修改，不能默认代表本轮改动前。历史基准与本轮前快照分开比较。
- 当前文件不一定是制作或运行时使用的版本。核对采用的规则、提示词、代码、配置及必要的模型或依赖版本，只追查会影响本例的部分。
- 当前新版、改前产物、失败候选和后续重制分别保留身份。缺失旧稿时不要拿新版、重建稿或旧评语代替原始证据。
- 多任务并发时辨认写入者和变更归属，不将所有工作区差异算到本次优化，不为取基线回滚共享工作区。

缺少可靠前版本时，继续检查当前执行与结果，但明确无法证实哪部分由本轮改动引入；不要补造前后差异。

## 3. 沿实际执行链定位偏差

围绕异常追踪「要求与规则 → 实际采用输入 → 工具处理 → 产物 → 验收与汇报」。按需要读取真实提示词、注入或转换逻辑、运行记录、源文件与实际成品，定位偏差第一次能被观察到的环节。

重点区分：

- **要求与采用**：规则是否适用于本任务，是否被加载，有无冲突、遗漏或歧义；不能只在当前文档里搜到一句要求便认定本次已遵守。
- **作者选择与工具处理**：异常在原始计划或提示词中是否已经写定，还是转换、模板注入、缓存或运行时行为造成。描述某个效果的制作说明不证明成品实现了它。
- **产物与验收**：按本次目标实际阅读、看图或观察运行结果，再核对验收记录。文件齐全、结构正确、测试通过与表达合格分别判断，不能互相替代。
- **判定与认可**：编辑判断、规则符合性和用户反馈保留各自范围。选择一个方向不等于认可整篇；单篇被否定也不证明整个流程退化。

结论引用具体位置、当时版本及可回查的观察。日志缺失时可结合已知代码解释可能机制，但不要把静态推断写成当时实际发生的事件。

## 4. 判断原因与证据强度

依据证据选择适用的原因，可并列：

| 原因 | 需要说明的关系 |
| --- | --- |
| 规则或流程设计 | 哪项新增、删除、冲突或歧义影响了本例选择，怎样导向观察到的问题；只有先后发生不能证明因果。 |
| 实现或生效版本 | 工具实际处理、版本未加载、错误入口或缓存如何让结果偏离预期；文件已改不等于运行已生效。 |
| 执行偏差 | 当时有效要求是什么，实际选择怎样偏离，有何输入、操作或产物证据。 |
| 验收误判 | 哪个目标未达到却被放行，验收用了什么替代判断；区分自动检查覆盖不足与审阅者判断失误。 |
| 输入或环境变化 | 任务难度、材料、平台、模型或其他条件是否同时改变，是否足以解释差异。 |

将已证实的直接原因、较有支持的解释和仍未排除的假设分开。主动检查会改变结论的反证，不因用户坚持、助手曾宣称成功或规则文字仍在就改写判断。执行存在失误不自动证明规则无责；未发现规则退化证据也不证明优化有效。

涉及版本混淆、提示词归属或误判边界时，按需阅读 [references/cases.md](references/cases.md)。示例用于帮助判断，不作为本次事实或固定结论。

## 5. 提出与原因对应的验证

优先给最小可区分假设的检查：核对实际加载版本、回查一处转换、比较同材料的前后处理，或在授权范围内重放代表实例。只读任务止于取证与建议；重放需要的写入、生成或外部操作仍按用户范围执行，不自动重跑整个生产流程。

需要对照时尽量保持输入、目标与环境一致，并记录不能控制的差异。模型生成等有波动的结果，不能靠一次重跑认定总体提升。已看过反馈的旧案例可用于回归，但不能称为盲测；声称方法能迁移前，须有未参与调整的新样本证据。

修复建议落到已证实的问题：补生效机制、调整确有歧义的规则、改变实际制作决策或校准验收。现有规则已明确但没有落实时，不默认继续叠加同义要求。保留原先有效的表现和能力，不从一例失败推出全量撤回。

## 6. 交付调查结论

按复杂度在对话或用户指定的现有记录中说明：

- 本次对象、比较版本与实际检查范围。
- 直接结论及「哪个环节做了什么 → 导致什么结果 → 为什么被放行」的证据链。
- 替代解释、反证和未知项，以及最小的下一步验证。
- 已授权修复时实际改了什么、如何复核，以及仍未验证的效果。

证据缺口不阻止给出有支持的局部结论，也不能被隐藏成确定归因。调查完成、单例修复、流程跑通和整体质量改善分别表述；不为归因任务强制新增报告体系或改造整个工程。
